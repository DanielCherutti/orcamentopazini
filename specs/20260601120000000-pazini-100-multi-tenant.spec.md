# PAZINI-100 — Multi-tenant da plataforma

**Branch:** `PAZINI-100`  
**Referências:** `00-global-context.spec.md`, `20260127231000000-auth-basic.spec.md`, `20260321120000000-portal-user-removal.spec.md`

## 1. Contexto e Objetivo

### 1.1 Contexto
- A visão do produto é **SaaS multitenant** (`00-global-context.spec.md`), mas o código atual opera como **instância única**:
  - `assertActionSession()` permite qualquer usuário autenticado ver todos os dados.
  - Catálogo usa `DEFAULT_COMPANY_ID = 0` fixo em produtos, grupos e unidades.
  - Orçamentos, clientes, biblioteca de imagens e `proposal_settings` **não** possuem isolamento por organização.
  - `portal_user` não tem vínculo com tenant nem role (Master / Admin / User).
  - Sessão JWT (`session-token.ts`) carrega apenas `sub` (e-mail), sem tenant ativo.

### 1.2 Objetivo
Introduzir **isolamento de dados por tenant** (organização) de forma incremental e segura, permitindo:
- Múltiplas organizações na mesma instância SurrealDB.
- Usuários vinculados a um ou mais tenants, com papel por tenant.
- Tenant ativo na sessão, com alternância na UI.
- Migração transparente dos dados atuais para um **tenant padrão** (Pazini legado).

### 1.3 Escopo desta entrega (PAZINI-100)

**Dentro:**
- Modelo `tenant` + membership usuário ↔ tenant + roles.
- Sessão com `tenant_id` ativo.
- Seletor de tenant no header (quando usuário tem >1 tenant).
- CRUD de tenants (apenas **Master**).
- Filtragem por tenant nas entidades principais.
- Script de migração/backfill para tenant padrão.
- Testes de regressão de isolamento (mínimo automatizado + roteiro manual).

**Fora (fases futuras):**
- OAuth/SSO, RBAC granular por recurso/ação.
- Audit log completo (`audit_log`) — preparar hooks, não implementar UI.
- Backup/restore por tenant (Master).
- Temas customizáveis por tenant.
- Rate limiting por tenant.
- Sharding / multi-database.

## 2. Modelo de domínio

### 2.1 Entidades novas

| Tabela | Descrição |
|--------|-----------|
| `tenant` | Organização isolada (nome, slug, ativo, soft delete) |
| `portal_user_tenant` | Vínculo N:N entre `portal_user` e `tenant` com `role` |

**Roles (v1):**

| Role | Escopo |
|------|--------|
| `master` | Acesso a todos os tenants; CRUD de tenants; pode operar em qualquer tenant |
| `admin` | Administra usuários e dados **do tenant** vinculado |
| `user` | Opera orçamentos/produtos/clientes **do tenant** vinculado |

> Um usuário pode ter memberships distintas em tenants diferentes (ex.: `admin` no tenant A, `user` no tenant B).  
> **Master** é global: membership com role `master` ignora restrição de tenant na listagem, mas operações mutáveis exigem tenant ativo na sessão.

### 2.2 Campo de isolamento

Padronizar **`tenant_id`** (`record<tenant>`) nas tabelas abaixo.

| Tabela | Situação atual | Ação |
|--------|----------------|------|
| `product` | `company_id: 0` | Adicionar `tenant_id`; manter `company_id` legado até fase de limpeza |
| `product_group` | `company_id: 0` | Idem |
| `product_unit` | `company_id: 0` | Idem |
| `client` | sem escopo | Adicionar `tenant_id` |
| `budget` | sem escopo | Adicionar `tenant_id` |
| `budget_*` (location, section, item, block, image) | herdam via `budget_id` | Validar tenant pelo budget pai (defesa em profundidade opcional em v1.1) |
| `image_library` | sem escopo | Adicionar `tenant_id` |
| `proposal_settings` | singleton global | Um registro **por tenant** |
| `portal_user` | global | Sem `tenant_id` direto; usar `portal_user_tenant` |

**Tenant padrão (migração):**
- ID sugerido: `tenant:pazini` (ou primeiro registro criado pelo script).
- Todo dado existente recebe `tenant_id = tenant:pazini`.
- Usuários `portal_user` existentes recebem membership `admin` (ou `user` — ver §11 Abertos) no tenant padrão.

### 2.3 Índices SurrealDB (mínimo)

```sql
DEFINE INDEX IF NOT EXISTS idx_tenant_slug ON tenant FIELDS slug UNIQUE;
DEFINE INDEX IF NOT EXISTS idx_portal_user_tenant_user ON portal_user_tenant FIELDS user_id;
DEFINE INDEX IF NOT EXISTS idx_portal_user_tenant_tenant ON portal_user_tenant FIELDS tenant_id;
DEFINE INDEX IF NOT EXISTS idx_product_tenant ON product FIELDS tenant_id;
DEFINE INDEX IF NOT EXISTS idx_client_tenant ON client FIELDS tenant_id;
DEFINE INDEX IF NOT EXISTS idx_budget_tenant ON budget FIELDS tenant_id;
DEFINE INDEX IF NOT EXISTS idx_image_library_tenant ON image_library FIELDS tenant_id;
DEFINE INDEX IF NOT EXISTS idx_proposal_settings_tenant ON proposal_settings FIELDS tenant_id;
```

## 3. Requisitos funcionais

### 3.1 Autenticação e sessão
- **RF-01:** Após login válido, o sistema resolve os tenants do usuário via `portal_user_tenant`.
- **RF-02:** Se o usuário tem **1 tenant**, define automaticamente como tenant ativo na sessão.
- **RF-03:** Se tem **>1 tenant**, redireciona para seleção de tenant (modal ou `/select-tenant`) antes do dashboard.
- **RF-04:** Se tem **0 tenants** e não é master, login falha com mensagem clara (“Sem acesso a nenhuma organização”).
- **RF-05:** Token de sessão passa a incluir `tenant_id` ativo e `role` no tenant (ou derivar role a cada request — preferir incluir no token com TTL curto e revalidar membership no servidor).
- **RF-06:** Master sem tenant selecionado pode acessar área de gestão de tenants; ao operar dados operacionais (produtos/orçamentos), deve escolher tenant ativo.

### 3.2 Seletor de tenant
- **RF-07:** Componente no header exibe nome do tenant ativo; dropdown lista tenants permitidos.
- **RF-08:** Trocar tenant atualiza cookie/sessão e recarrega contexto (redirect para `/dashboard` ou página atual se pertencer ao tenant).
- **RF-09:** Dados de outro tenant **nunca** aparecem após troca.

### 3.3 Gestão de tenants (Master)
- **RF-10:** Rota `/dashboard/tenants` (ou seção em Configurações) — lista, cria, edita, inativa tenant.
- **RF-11:** Campos: `name` (obrig.), `slug` (obrig., único, kebab-case), `active` (bool).
- **RF-12:** Soft delete: `deleted_at`; tenant deletado não aparece em seletores.
- **RF-13:** Master associa usuários existentes a tenants (role admin/user) — UI mínima ou extensão da tela de usuários.

### 3.4 Isolamento de dados (Server Actions)
- **RF-14:** Toda Server Action que lê/escreve dados de negócio exige sessão **e** tenant ativo resolvido (`assertTenantSession()`).
- **RF-15:** Queries de listagem filtram `WHERE tenant_id = $tenantId` (ou join via budget).
- **RF-16:** Create sempre persiste `tenant_id` do contexto; **nunca** confiar em `tenant_id` vindo do client sem validar membership.
- **RF-17:** Get/update/delete por ID valida que o registro pertence ao tenant ativo (anti-IDOR).
- **RF-18:** Master pode acessar qualquer tenant **desde que** `tenant_id` ativo na sessão corresponda ao recurso (troca explícita).

### 3.5 Convites e usuários
- **RF-19:** Convite de usuário (`portal-invite-actions`) associa ao **tenant ativo** do admin que convida.
- **RF-20:** E-mail continua único globalmente em `portal_user`; memberships são por tenant.
- **RF-21:** Remoção de usuário do portal (spec existente) permanece global; remover membership é ação separada por tenant (admin do tenant).

### 3.6 Compatibilidade
- **RF-22:** Instalações existentes continuam funcionando após migração + seed de tenant padrão.
- **RF-23:** Seeds (`seed:portal-user`, `seed:products`) aceitam tenant padrão ou variável `PAZINI_DEFAULT_TENANT_SLUG`.

## 4. Contratos e interfaces

### 4.1 Sessão (evolução de `session-token.ts`)

Payload v2 (proposta):

```typescript
{
  v: 2,
  sub: string,           // email
  tenant_id: string,     // record id tenant:...
  role: "master" | "admin" | "user",
  exp: number
}
```

- Manter compatibilidade: tokens v1 (só `sub`) invalidados no deploy — forçar re-login.
- Cookie httpOnly existente (`SESSION_COOKIE`).

### 4.2 Helpers server-side (novos)

| Função | Responsabilidade |
|--------|------------------|
| `getSessionContext()` | `{ email, tenantId, role }` ou null |

## 5. Fluxos

### 5.1 Login — usuário com um tenant
1. Login e-mail/senha OK.
2. Sistema encontra 1 membership.
3. Emite sessão v2 com `tenant_id` + `role`.
4. Redirect `/dashboard`.

### 5.2 Login — usuário com vários tenants
1. Login OK.
2. Sistema encontra N memberships.
3. Redirect `/select-tenant` com lista.
4. Usuário escolhe → `switchTenantAction` → dashboard.

### 5.3 Master cria novo tenant
1. Master acessa `/dashboard/tenants`.
2. Cria tenant “Engenharia XYZ” slug `engenharia-xyz`.
3. Associa usuário admin inicial.
4. Admin faz login e opera apenas no tenant XYZ.

### 5.4 Tentativa de IDOR
1. Usuário tenant A tenta `GET budget` com ID de tenant B.
2. Action valida `budget.tenant_id !== session.tenant_id`.
3. Retorno `{ success: false, error: "Não encontrado" }` (404 semântico, sem vazar existência).

## 7. Migração

### 7.1 Script `migrate-multi-tenant.ts`
1. Criar tenant padrão se não existir (`slug: pazini`, `name: Pazini`).
2. `UPDATE` em lote: `product`, `product_group`, `product_unit`, `client`, `budget`, `image_library` sem `tenant_id`.
3. Clonar ou criar `proposal_settings` para tenant padrão se singleton existir.
4. Para cada `portal_user` ativo: criar `portal_user_tenant` com role `admin` no tenant padrão (ajustável via flag).
5. Modo dry-run: `MIGRATE_DRY_RUN=1` (já usado no projeto).

### 7.2 Rollback
- Restaurar backup SurrealDB (`npm run backup:db` antes da migração).
- Reverter deploy de código sem sessão v2.
- **Não** remover colunas `tenant_id` em rollback parcial — manter compatibilidade.

### 7.3 Ordem de deploy
1. Backup DB.
2. Deploy código com schema + script (dry-run).
3. Executar migração.
4. Deploy frontend com sessão v2 (usuários re-login).
5. Smoke test manual.

## 8. NFRs

- **Segurança:** Zero trust no client para `tenant_id`; validação server-side em 100% das mutations e reads por ID.
- **Performance:** Índices em `tenant_id`; listagens paginadas mantidas.
- **Observabilidade:** Log estruturado em negações de tenant (`tenant_mismatch`, `missing_membership`) sem dados sensíveis.
- **Compatibilidade:** SurrealDB v3.0.4; sem novas dependências pesadas.

## 9. Guardrails

- Seguir SDD: specs antes de código (este documento).

- Não importar SurrealDB em Client Components.
- Commits Conventional Commits: `feat(tenant): ...`.
