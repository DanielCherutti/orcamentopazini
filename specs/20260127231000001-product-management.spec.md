# 20260127231000001 - Gestão de Produtos

Esta especificação define os requisitos funcionais e técnicos para o módulo de Gestão de Produtos do sistema Pazini.

## 1. Objetivo
Implementar um CRUD completo de produtos com suporte a descrições ricas (Rich Text), upload de imagens e gerenciamento de arquivos anexos, garantindo uma experiência de usuário organizada e fluida.

## 2. Requisitos de UI (Frontend)

### 2.0 Listagem de Produtos (Index)
- **Filtros e Busca:**
    - Campo de busca textual por **Código** ou **Descrição**.
    - Busca deve ser "debounced" (300ms) para evitar excesso de requisições.
- **Paginação:**
    - Listagem paginada no servidor (Server-Side Pagination).
    - Limite padrão: **10 itens por página**.
    - **Componente de Paginação Completo:**
        - **Seletor de Itens por Página:**
            - Dropdown com opções: 10, 20, 50, 100 itens por página.
            - Deve persistir a escolha do usuário durante a sessão.
            - Ao alterar, retorna para a página 1.
        - **Navegação entre Páginas:**
            - Botão "Primeira" (<<) - navega para página 1.
            - Botão "Anterior" (<) - navega para página anterior (desabilitado na página 1).
            - **Indicador de Página Atual:** Exibe "Página X de Y".
            - Botão "Próxima" (>) - navega para próxima página (desabilitado na última página).
            - Botão "Última" (>>) - navega para última página.
        - **Informações de Registros:**
            - Exibe "Mostrando X-Y de Z produtos" (ex: "Mostrando 1-10 de 54 produtos").
            - Atualiza dinamicamente conforme navegação e filtros.
        - **Comportamento:**
            - Ao aplicar filtro de busca, retorna para página 1.
            - Botões desabilitados visualmente quando não aplicáveis.
            - Transição suave entre páginas com loading state.
- **Feedback Visual:**
    - Exibir "Nenhum produto encontrado" caso a busca não retorne resultados.
    - Indicador de carregamento (Skeleton ou Spinner) ao trocar de página ou buscar.

### 2.1 Estrutura do Formulário
- **Organização:** O formulário de cadastro e edição deve ser organizado em **Abas (Tabs)** para melhor usabilidade:
  1.  **Aba Básico:** Informações principais e imagem de capa.
  2.  **Aba Descrição:** Editor de texto rico para manuais e detalhamento.
  3.  **Aba Anexos:** Lista e upload de arquivos complementares (PDFs, Docs, etc).

### 2.2 Aba Básico
- **Campos Obrigatórios:**
  - `code` (Texto): Código único do produto.
  - `unit` (Texto): Unidade de medida (ex: UN, M, M²).
  - `description` (Texto): Descrição resumida do produto.
  - `equipmentPrice` (Moeda): Valor do equipamento (BRL).
  - `assemblyPrice` (Moeda): Valor da montagem (BRL).
- **Campo Grupo (Opcional):**
  - Seletor em lista (Combobox) com grupos cadastrados.
  - Deve permitir **cadastro de novo grupo** quando a opção desejada não existir (ver `20260202120000000-product-groups.spec.md`).
- **Imagem de Capa:**
  - Componente de upload para a imagem principal do produto.
  - **Upload imediato:** Ao selecionar a imagem, o sistema deve fazer upload imediatamente para a pasta temporária `products/pending/` e exibir a preview com a URL real (não apenas objectUrl). O produto será criado com essa URL já associada.
  - Funcionalidades: Pré-visualização (preview) imediata, substituição e remoção da imagem.
  - Validação: Formatos de imagem comuns (JPG, PNG, WEBP), tamanho máximo 5MB.

### 2.3 Aba Descrição Detalhada
- **Editor de Texto Rico:**
  - Utilizar biblioteca **Tiptap** para edição de conteúdo HTML.
  - **Barra de Ferramentas:**
    - Formatação de texto: Negrito, Itálico, Sublinhado.
    - Estrutura: Títulos (H1, H2, H3), Listas (Bullet e Numerada).
    - Mídia: Inserção de imagens diretamente no corpo do texto (com upload automático).

### 2.4 Aba Anexos
- **Gerenciador de Arquivos:**
  - Lista de arquivos anexados ao produto.
  - Ações por arquivo: Download e Exclusão.
  - Botão de upload para adicionar novos arquivos.
  - Suporte a múltiplos tipos de arquivo (PDF, imagens, documentos de texto).

## 3. Requisitos de Dados e Backend

### 3.1 Modelo de Dados (Schema)
Os produtos devem ser armazenados com a seguinte estrutura (compatível com SurrealDB):

```typescript
type Product = {
  id: string;              // Identificador único (ex: product:uuid)
  company_id: number;      // Identificador da empresa (Valor padrão: 0)
  code: string;            // Código do produto
  description: string;     // Nome/Descrição curta
  detailedDescription?: string; // Conteúdo HTML do editor rico
  unit: string;            // Unidade de medida
  equipmentPrice: number;  // Valor decimal
  assemblyPrice: number;   // Valor decimal
  imageUrl?: string;       // Caminho relativo da imagem de capa
  group_id?: string;       // record<product_group> - Grupo do produto (ver spec product-groups)
  attachments?: Attachment[]; // Lista de anexos
  created_at: string;      // Data ISO
  updated_at: string;      // Data ISO
}

type Attachment = {
  id: string;       // UUID gerado para o anexo
  filename: string; // Nome original do arquivo
  url: string;      // Caminho relativo para acesso
  type: string;     // MIME type
}
```

### 3.2 Operações (Server Actions)
- `createProduct`: Recebe os dados do formulário, processa uploads iniciais e cria o registro.
- `updateProduct`: Atualiza os dados do produto, incluindo modificações na lista de anexos e troca de imagem.
- `deleteProduct`: Remove o registro do produto e, mandatoriamente, exclui todos os arquivos associados (imagem de capa e anexos) do armazenamento.

### 3.3 Uploads e Armazenamento
- O sistema deve fornecer Endpoints de API (`/api/upload/...`) ou Server Actions dedicadas para processar o recebimento de arquivos binary/multipart.
- Arquivos devem ser salvos em diretórios organizados (ex: `public/uploads/products/[id]/`).
- É necessário validar tipos de arquivo e tamanhos permitidos no backend.
- **Endpoint de upload temporário:** `POST /api/upload/product/pending` — aceita upload sem `productId`; salva em `public/uploads/products/pending/{uuid}.{ext}`; retorna `{ url: string }`. Arquivos em `products/pending/` são considerados temporários e podem ser removidos por job de limpeza (órfãos).



### 3.4 Validação e Feedback
- **Feedback de Erro:**
  - O sistema deve validar os campos obrigatórios e formatos (números, datas) server-side e client-side.
  - **Validação Schema:** Utilizar **Zod** para definir e validar o schema do produto no servidor.
  - **Formato de Erro:** As Actions devem retornar erros estruturados: `{ success: false, error: "Mensagem Geral", fieldErrors: { code: ["Erro detalhado"] } }`.
  - **UI:**
    - Erros globais devem ser exibidos em um componente de **Alert** no topo do formulário.
    - Erros específicos de campo devem ser exibidos em texto vermelho logo abaixo do input correspondente e destacar a borda do input.
  - **Toast:** Mensagens de sucesso devem utilizar o componente `sonner` (Toast).

## 4. Workflows e Ações

### 4.1 Cadastro (Create)
1. Usuário acessa `/dashboard/products/new`.
2. Preenche o formulário.
3. **Opcional:** Usuário pode selecionar imagem antes de salvar; o upload é feito imediatamente e a URL é armazenada no estado do formulário.
4. Ao salvar, o botão exibe estado de "Salvando...". Se `imageUrl` já estiver preenchido (de upload prévio), usa essa URL; caso contrário, processa `imageFile` do FormData se existir.
5. Se sucesso -> Redireciona para `/dashboard/products` com toast de "Produto criado com sucesso!".
6. Se erro -> Mantém na página, exibe Alert de erro e erros nos campos (se houver), preservando dados digitados.

### 4.2 Edição (Update)
1. Usuário clica em um produto na lista ou botão "Editar".
2. Url: `/dashboard/products/[id]`.
3. O formulário vem preenchido com dados atuais.
4. Ao salvar -> Atualiza dados, revalida cache e redireciona com toast de sucesso.
5. Em caso de erro, segue o mesmo padrão do cadastro.

### 4.3 Exclusão (Delete)
1. Disponível na tela de edição (botão "Excluir Produto" vermelho).
2. **Confirmação:** Deve exibir um **Dialog de Confirmação** (AlertDialog) perguntando "Você tem certeza?".
3. **Pós-Exclusão:** Se confirmado, remove arquivos e registro, redireciona para listagem com toast de sucesso.

## 6. Critérios de Robustez e Verificação
### 6.1 Garantia de Persistência
- Todo cadastro onde os campos obrigatórios (Código, Descrição, Preços) estejam preenchidos **DEVE** resultar em um registro salvo no banco de dados.
- O sistema **DEVE** validar o sucesso da operação no backend antes de redirecionar.
- Em caso de falha no banco de dados, o usuário **DEVE** ser notificado com uma mensagem de erro clara, e os dados do formulário **NÃO** devem ser perdidos.

### 6.2 Fluxo de Verificação
1. **Preenchimento:** Usuário preenche formulário completo.
2. **Submissão:** Clica em "Salvar".
3. **Persistência:** Backend valida e salva no SurrealDB.
4. **Confirmação:** Toast de sucesso.
5. **Redirecionamento:** Usuário é redirecionado para a listagem.
6. **Listagem:** O novo produto **DEVE** aparecer imediatamente na lista (revalidação de cache).
