# 20260219120000000 - Gestão de Clientes

Esta especificação define os requisitos funcionais e técnicos para o módulo de Gestão de Clientes do sistema Pazini, incluindo CRUD completo com busca de endereço por CEP via ViaCEP e integração com o seletor de clientes nos orçamentos.

## 1. Contexto e Objetivo

- **Contexto:** O sistema já possui um seletor de clientes nos orçamentos (`ClientSelector`) que consome dados do SurrealDB via `searchClientsAction`. Os clientes são cadastrados com campos mínimos (nome, email, cidade, CNPJ). Não existe ainda uma página de gestão (listagem + CRUD) de clientes acessível no menu principal.
- **Objetivo:** Criar um menu "Clientes" no sistema com CRUD completo: listagem, cadastro, edição e exclusão de clientes com dados fiscais, de contato e endereço completo. O endereço deve ser preenchido automaticamente via API ViaCEP ao digitar o CEP, com possibilidade de edição manual de todos os campos.
- **Escopo desta entrega:**
  - Rota `/customers` com listagem paginada e busca
  - Formulário de cadastro/edição em `/customers/new` e `/customers/[id]/edit`
  - Server Actions para CRUD completo
  - Integração com ViaCEP no lado cliente (fetch da API pública)
  - Atualização do schema SurrealDB para suportar novos campos
  - Compatibilidade com `ClientSelector` existente nos orçamentos
- **Fora de escopo:**
  - Importação em lote de clientes (CSV/Excel)
  - Histórico de orçamentos por cliente (listagem no perfil)
  - Validação de CNPJ via Receita Federal
  - Gestão de múltiplos endereços por cliente

## 2. Requisitos Funcionais

### 2.1 Listagem de Clientes (`/customers`)

- Exibe todos os clientes cadastrados em tabela paginada (padrão: 10 itens/página).
- Colunas visíveis: **Nome**, **CNPJ**, **Cidade/UF**, **Telefone**, **E-mail**, **Ações**.
- Campo de busca textual por nome, CNPJ ou e-mail (debounce 300ms).
- Estado da busca e paginação mantido na URL (`?query=`, `?page=`, `?limit=`).
- Ações por linha: **Editar** (ícone lápis) e **Excluir** (ícone lixeira com confirmação).
- Estado vazio: mensagem "Nenhum cliente encontrado." com botão "Cadastrar primeiro cliente".
- Botão "Novo Cliente" fixo no topo direito, navega para `/customers/new`.
- Ao excluir: dialog de confirmação → Server Action → toast de sucesso/erro → atualiza lista.

### 2.2 Formulário de Cadastro/Edição

O formulário é exibido em página dedicada (não modal) com os seguintes campos agrupados em seções:

#### Seção: Dados da Empresa
| Campo | Label | Tipo | Obrigatório | Validação |
|---|---|---|---|---|
| `name` | Nome / Razão Social | Texto | Sim | Mínimo 2 caracteres |
| `cnpj` | CNPJ | Texto (máscara) | Sim | Formato XX.XXX.XXX/XXXX-XX; único no sistema |
| `stateRegistration` | Inscrição Estadual | Texto | Não | Livre (aceitar "ISENTO") |

#### Seção: Contato
| Campo | Label | Tipo | Obrigatório | Validação |
|---|---|---|---|---|
| `contact` | Nome do Contato | Texto | Não | — |
| `phone` | Telefone | Texto (máscara) | Não | Formato (XX) XXXXX-XXXX ou (XX) XXXX-XXXX |
| `email` | E-mail | Email | Não | Formato de e-mail válido |

#### Seção: Endereço

O primeiro campo da seção é o CEP. Ao preencher 8 dígitos e sair do campo (blur), o sistema consulta a API ViaCEP e preenche automaticamente os campos abaixo. Todos os campos preenchidos automaticamente são editáveis pelo usuário.

| Campo | Label | Tipo | Obrigatório | Notas |
|---|---|---|---|---|
| `address.cep` | CEP | Texto (máscara) | Não | Máscara XXXXX-XXX; ao blur com 8 dígitos → busca ViaCEP |
| `address.street` | Logradouro | Texto | Não | Preenchido pelo ViaCEP (`logradouro`) |
| `address.number` | Número | Texto | Não | Preenchido manualmente |
| `address.complement` | Complemento | Texto | Não | Preenchido pelo ViaCEP (`complemento`) se existir |
| `address.neighborhood` | Bairro | Texto | Não | Preenchido pelo ViaCEP (`bairro`) |
| `address.city` | Cidade | Texto | Não | Preenchido pelo ViaCEP (`localidade`) |
| `address.state` | Estado (UF) | Texto (2 chars) | Não | Preenchido pelo ViaCEP (`uf`); uppercase |

**Comportamento do CEP:**
- Ao iniciar a busca no ViaCEP: exibir indicador de loading no campo CEP.
- Se CEP inválido/não encontrado: exibir mensagem inline "CEP não encontrado. Preencha o endereço manualmente." e manter campos editáveis.
- Se CEP válido: preencher campos e mover foco para o campo "Número".
- A busca é feita no **lado cliente** via `fetch` para `https://viacep.com.br/ws/{cep}/json/`.

### 2.3 Exclusão de Cliente

- Dialog de confirmação com nome do cliente exibido.
- Exclusão lógica (soft delete) **não** é necessária nesta entrega — exclusão física com verificação de referências.
- Se o cliente estiver referenciado em algum orçamento: exibir erro "Não é possível excluir: cliente possui orçamentos vinculados." e não excluir.

### 3.3 Schema Zod (validação de entrada)

```typescript
const AddressSchema = z.object({
  cep:          z.string().optional(),
  street:       z.string().optional(),
  number:       z.string().optional(),
  complement:   z.string().optional(),
  neighborhood: z.string().optional(),
  city:         z.string().optional(),
  state:        z.string().max(2).optional(),
});

const ClientFormSchema = z.object({
  name:              z.string().min(2, "Nome obrigatório"),
  cnpj:              z.string().min(14, "CNPJ inválido"),
  stateRegistration: z.string().optional(),
  contact:           z.string().optional(),
  phone:             z.string().optional(),
  email:             z.string().email("E-mail inválido").optional().or(z.literal("")),
  address:           AddressSchema.optional(),
});
```

### 3.4 Banco de Dados (SurrealDB)

**Tabela:** `client`

Campos existentes mantidos por compatibilidade: `name`, `email`, `city`, `cnpj`.

Novos campos adicionados (campo `city` passa a ser derivado de `address.city` na leitura):

```surql
DEFINE FIELD contact          ON TABLE client TYPE option<string>;
DEFINE FIELD phone            ON TABLE client TYPE option<string>;
DEFINE FIELD stateRegistration ON TABLE client TYPE option<string>;
DEFINE FIELD address          ON TABLE client FLEXIBLE TYPE option<object>;
DEFINE FIELD address.cep          ON TABLE client TYPE option<string>;
DEFINE FIELD address.street       ON TABLE client TYPE option<string>;
DEFINE FIELD address.number       ON TABLE client TYPE option<string>;
DEFINE FIELD address.complement   ON TABLE client TYPE option<string>;
DEFINE FIELD address.neighborhood ON TABLE client TYPE option<string>;
DEFINE FIELD address.city         ON TABLE client TYPE option<string>;
DEFINE FIELD address.state        ON TABLE client TYPE option<string>;
```

**Migração:** O campo `city` legado não é removido — a action `searchClientsAction` já o usa. Novos clientes terão `city` populado a partir de `address.city` automaticamente para manter retrocompatibilidade com o `ClientSelector`.

**Índice de unicidade para CNPJ:**
```surql
DEFINE INDEX idx_client_cnpj ON TABLE client COLUMNS cnpj UNIQUE;
```

### 3.5 Compatibilidade com `ClientSelector`

A função `searchClientsAction` deve ser atualizada para buscar também por `address.city` quando `city` estiver vazio. As Server Actions de criação/edição devem sempre gravar `city = address.city` no nível raiz do documento para compatibilidade.

## 4. Fluxos e Estados

### 4.1 Fluxo: Criar Cliente com CEP

1. Usuário acessa `/customers/new`.
2. Preenche Nome e CNPJ.
3. Na seção Endereço, digita CEP (ex: `01310-100`).
4. Ao sair do campo (blur): spinner aparece no campo CEP.
5. ViaCEP retorna dados → campos de logradouro, bairro, cidade, estado preenchidos automaticamente.
6. Usuário preenche Número e ajusta campos se necessário.
7. Clica em "Salvar" → `createClientAction` → sucesso → redireciona para `/customers` com toast "Cliente criado com sucesso."

### 4.2 Fluxo: CEP inválido

1. Usuário digita CEP inexistente.
2. ViaCEP retorna `{ "erro": "true" }`.
3. Sistema exibe mensagem inline abaixo do campo CEP: "CEP não encontrado. Preencha o endereço manualmente."
4. Campos de endereço ficam vazios e editáveis.

### 4.3 Fluxo: Editar Cliente

1. Usuário clica em "Editar" na listagem.
2. Navega para `/customers/[id]/edit` → RSC carrega dados via `getClientAction`.
3. Form populado com dados existentes.
4. Usuário altera campos → "Salvar" → `updateClientAction` → toast "Cliente atualizado." → retorna para `/customers`.

### 4.4 Fluxo: Excluir Cliente

1. Usuário clica em ícone de lixeira na linha do cliente.
2. Dialog: "Tem certeza que deseja excluir **[Nome]**? Esta ação não pode ser desfeita."
3. Botões: "Cancelar" | "Excluir" (destrutivo, vermelho).
4. Confirma → `deleteClientAction` → sucesso: toast "Cliente excluído." + remove da lista. Erro: toast com mensagem de erro.

### 4.5 Estados de Erro

- CNPJ duplicado: erro inline no campo "CNPJ já cadastrado no sistema."
- Campos obrigatórios vazios: erros inline por campo.
- Erro de servidor: toast "Erro ao salvar cliente. Tente novamente."
- Timeout no ViaCEP (> 5s): mensagem "Serviço de CEP indisponível. Preencha o endereço manualmente." e campos liberados.

## 6. NFRs (Não Funcionais)

- **Desempenho:** Listagem de clientes carrega em < 500ms. Consulta ViaCEP tem timeout de 5 segundos.
- **Segurança:** Acesso às rotas exige autenticação (middleware existente). Todas as entradas validadas via Zod nas Server Actions. CNPJ não é logado em texto completo.
- **Acessibilidade:** Campos de formulário com `label` associado e `aria-describedby` para mensagens de erro.
- **Responsividade:** Layout funcional em telas ≥ 375px. Tabela com scroll horizontal em mobile.
- **Observabilidade:** Erros em Server Actions logados no servidor com `console.error`. Erros ViaCEP logados no cliente com `console.warn`.

## 7. Guardrails

- **Stack:** Não adicionar novas dependências. A busca ViaCEP usa `fetch` nativo do browser.
- **Convenções:**
  - Rota em `app/(main)/customers/` (sem prefixo `dashboard/`, igual ao padrão de `budgets/`)
  - Server Actions em `actions/client-actions.ts` (arquivo existente, expandido)
  - Componentes em `components/clients/`
  - Seguir padrão URL-first para paginação/busca (ver `02-listing-ui-pattern.spec.md`)
- **Padrões:** Tratamento de erros via toast (Sonner/shadcn). Confirmação de exclusão via `AlertDialog` (shadcn).
- **Máscara de campos:** Usar lógica simples de formatação via `onChange` sem bibliotecas de máscara externas (onMaskChange helper local). CNPJ: `XX.XXX.XXX/XXXX-XX`. Telefone: `(XX) XXXXX-XXXX`.

- [ ] `/customers` lista todos os clientes com paginação funcional (10/página por padrão).
- [ ] Busca por nome, CNPJ ou e-mail filtra resultados em tempo real (debounce 300ms).
- [ ] Estado de busca e página refletidos na URL e mantidos ao navegar.
- [ ] Botão "Novo Cliente" navega para `/customers/new`.
- [ ] Clicar em "Editar" navega para `/customers/[id]/edit` com dados do cliente populados.

- [ ] Confirmar exclusão remove o cliente da lista e exibe toast de sucesso.
- [ ] Estado vazio exibe mensagem e link para criação.

### Formulário — Validação
- [ ] Salvar com "Nome" vazio exibe erro inline no campo.
- [ ] Salvar com "CNPJ" vazio ou inválido exibe erro inline no campo.
- [ ] Salvar com CNPJ já cadastrado exibe erro inline "CNPJ já cadastrado no sistema."

### Formulário — CEP / Endereço
- [ ] Digitar CEP válido e sair do campo exibe loading e preenche logradouro, bairro, cidade, estado automaticamente.

- [ ] Ao criar cliente com endereço, o campo `city` raiz é preenchido com `address.city` (retrocompatibilidade com ClientSelector).

- [ ] `ClientSelector` nos orçamentos continua funcionando e exibe clientes criados pelo novo CRUD.
- [ ] Busca no `ClientSelector` encontra clientes pelo nome, e-mail, CNPJ ou cidade.

- [ ] Cliente vinculado a orçamento não é excluído; exibe mensagem de erro adequada.
